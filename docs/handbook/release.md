# 发布与版本

> **管什么**：怎么把新版交给所有者用；版本号；更新日志；签名和密钥放在哪；以后对外发布的流程。
> **什么时候更新**：交付方式变了、加了新的密钥或证书、第一次给别人装之前（写“对外发布”一节）。
> **上次复核**：2026-10-18

现在是自用阶段，没有对外发布。依据见调研 [附录 B](../research/2026-10-appendix-b-lifecycle.md) 第 6~8 节。

## 给所有者用新版

所有者定的（2026-10-18）：签名编译好就行，不打 dmg，`.app` 放在主文件夹的 `build/` 里。

- `scripts/mac-reopen.sh`：签名编译 → 放进主文件夹的 `build/EverShell.app`（在 worktree 里跑也搬到那里，所有者只认这一个位置）→ 退出他正在用的旧版 → 打开新版。release 编译要几分钟，用 `run_in_background` 跑。
- 电脑上只留 `build/` 这一份应用（所有者 2026-10-23 定）：编译的中间产物 `target/release/bundle/macos/EverShell.app` 复制完就删，worktree 里编的是搬过去、不留副本。别处多出来的应用会出现在访达和聚焦搜索里，他分不清该开哪个。
- 不先退出旧版的话，系统只会把旧窗口叫到前面，打开的还是旧版。别的会话开着的调试版不受影响。

**跑之前查两件事**：

1. **编进去的是不是都该编进去。** 它编的是当前文件夹里的全部代码。在共享文件夹里，`git status` 看有没有别的会话没写完的改动，有就先问所有者。在 worktree 里，它不带主文件夹上没提交的改动，编出来可能比所有者手上那版还旧，同样先问。
2. **所有者的 EverShell 开着没有**：`pgrep -f build/EverShell.app`。开着就先问他（重开会断开他正在用的连接），等他说可以再跑；没开就直接跑。
- 只想重开不编译：`scripts/mac-reopen.sh --no-build`。
- 交付时告诉所有者：改了什么、来自哪个分支、请他试哪几步。

## 版本号

- 应用的版本号以 `apps/desktop/src-tauri/tauri.conf.json` 的 `version` 为准，现在是 0.1.0。各个 `package.json` 和 Rust crate 的版本号是内部用的，不用跟着改。
- **只用纯数字的 X.Y.Z**，不加 `-beta` 这类后缀：Windows 的 MSI 安装包和 App Store 都不接受。以后测试版和正式版靠更新渠道区分，同一个包先发测试渠道，没问题再推到正式渠道（附录 B 8.1）。
- 1.0 之前用 0.y.z。自用阶段交付不升版本号；第一次给别人装时再定升版规则。

## 更新日志

- 根目录 `CHANGELOG.md`，中文，**写给用户看**：每个用户能看到的变化写一行，以“新增”“修复”“优化”开头，不写内部细节（照 Clash Verge Rev 的写法，附录 A 3.3）。
- 交付给所有者时（[process.md](process.md#6-交付)），在“未发布”下面加一行。所有者不读代码，这份日志就是他了解“这次改了什么”的地方，以后也能直接用作应用里的更新说明。
- 纯内部的改动（重构、测试、开发脚本、文档）不写。
- 几个会话可能同时往“未发布”里加，只追加自己的一行，不改别人的；在 worktree 里写的随分支一起合并。
- 发版时把“未发布”改成版本号和日期。

## 签名和密钥

**只记放在哪、丢了怎么办，不写密钥本身。** 加了新的密钥或证书，在这里补一行。

| 东西 | 用在哪 | 放在哪 | 丢了或泄露了 |
|---|---|---|---|
| Developer ID Application 证书 | 正式版签名（`tauri.macos.conf.json` 的 `signingIdentity`）、开发版签名（`scripts/macos-dev-run`） | 所有者这台 Mac 的登录钥匙串 | 在 Apple 开发者后台重新申请；换证书后，钥匙串里保存的钥匙可能要重新点一次“始终允许” |
| Apple 开发者账号 | 证书、以后的公证、TestFlight | 所有者 | |

以后会有的（到时候补进上表）：

- **公证用的 App Store Connect API 密钥**：CI 里公证用它，不用所有者的 Apple ID 密码。
- **自动更新的签名私钥**：**丢了无法挽回**，已经装了的用户再也收不到更新，所以生成后离线备份两份。泄露了还能用旧私钥签一版过渡版换新钥匙。只放在 GitHub 的受保护环境里，每次发布要所有者在网页上批准（附录 B 第 7、12 节）。
- Cloudflare API 令牌（同步服务、中转部署）、Windows 签名证书。

## 对外发布（第一次给别人装之前写）

占位。调研的结论（附录 B 第 6~8 节），写这一节时作为起点：

- **Mac 只走 Developer ID 直接分发**，建议不上 Mac App Store（沙盒限制，加上 GPL 和商店条款冲突）。要所有者定。
- **公证**：Tauri 打包时设好环境变量会自动公证和 staple；打 dmg 也要签名；在一台干净的 Mac 上验证双击能打开、没有警告。
- **自动更新**：Tauri updater 插件；正式渠道的更新清单放 GitHub Releases，测试渠道单独一份（GitHub 的“最新版本”会跳过预发布）；清单里任何一个平台的条目不完整，所有平台都更新失败；桌面端不能回滚，只能发更高版本号的修复版，所以每次发版前实测“从上一版自动升到这一版”。
- **流程**：推 tag → 构建、签名、公证 → 生成草稿 Release → 所有者下载验收 → 发布。同类项目几乎都这样做（附录 A 3.1）。写一份发布检查单，第一次发版就照着走。
- **最低支持的 macOS 版本**、隐私说明（哪些数据会离开设备）也在这时定。
