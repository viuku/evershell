# 产品与边界

> **管什么**：EverShell 是什么、给谁用、做取舍时的原则、明确不做什么。功能清单和里程碑在 [requirements.md](../requirements.md)，这里不重复。
> **什么时候更新**：所有者改了产品方向，或者定了新的原则、新的边界。
> **上次复核**：2026-10-18

## 一句话

FinalShell 风格的 SSH 客户端：终端、文件管理、服务器监控在一个窗口里。不会停更跑路，数据握在用户自己手里。

## 给谁用

- **现在**：所有者自己。他管着多台 Linux 服务器，是中文用户，要拿它日常替代 FinalShell。
- **以后**：想离开 FinalShell 的中文运维和开发者；可能还有不想自建、直接用所有者托管同步服务的人，所以同步从第一版就按多账号设计。
- **谁来开发**：所有者不写代码，全部代码由 AI 写。所有者看界面、看结果、拍板。

## 产品原则

原则之间冲突时，排在前面的优先。

1. **安全第一。** 软件里存着能登录服务器的密码和私钥。方便和安全冲突时选安全，再想办法让安全不麻烦，比如钥匙放系统钥匙串，用户不用每次输主密码。具体规矩见 [security.md](security.md)。
2. **数据永远带得走。** 这就是“不跑路”：
   - 不依赖任何官方服务器也能用；同步服务用户可以自建（Docker，或者自己的 Cloudflare 账号）。
   - 用户的数据随时能导出成格式公开的文件，导出再导回不丢东西（见 [data.md](data.md)）。
   - 不收集使用数据。以后要加任何会离开本机的功能（检查更新、崩溃上报），先问所有者，默认关闭，写清楚发出去的是什么。
3. **全平台，一个一个来。** Mac → 网页 → Windows → 手机。现在只做 Mac，但不能把其他平台堵死，具体做法是 [architecture.md](architecture.md) 的跨平台守则。
4. **交互照搬 FinalShell，外观换成 Mac 原生风格。** 布局和操作逻辑以 FinalShell 为准，视觉以定稿设计稿 [docs/design](../design) 为准。不自己发明 FinalShell 没有的交互结构；要加新东西，先出设计稿给所有者挑（见 [process.md](process.md)）。
5. **服务器上什么都不装。** 监控靠 SSH 执行命令采集，跟 FinalShell 一样。

## 明确不做

- 需求文档 3.6 列的：Telnet / 串口、本阶段的手机客户端、FinalShell 的付费附加功能。
- **不假装断线没发生。** 断线就如实显示，重连建一个新会话（可以自动接回 tmux），不做协议层面的“会话恢复”。原因见调研附录 C 第 3.2 节：[附录 C](../research/2026-10-appendix-c-ssh-client-concerns.md)。
